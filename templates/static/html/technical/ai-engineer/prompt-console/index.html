03 / Method

Measure first, prompt second.

A prompt change is a product change, and it needs the same evidence as one: a set of cases that failed before, a metric that is allowed to regress, and a cost line that a finance team can read.

I start with twenty real failures, not twenty imagined ones. If the eval set cannot be built from production traffic, the feature is not ready for an eval — it is still a prototype.

How the work runs

  1. 01

    Collect the failures

    Twenty to two hundred real requests with the wrong answer, the model's reasoning, and what the right answer was. This set is the only thing that decides whether a change is an improvement.

  2. 02

    Make the metric honest

    Exact match where the output is structured, rubric grading where it is prose, and a separate refusal metric. Inter-annotator agreement on a sample, or the metric is a guess.

  3. 03

    Cut the context

    Shorter prompts are faster, cheaper and usually more accurate. Few-shot examples earn their tokens only when the failure set proves it; retrieval earns them only when the chunk is actually cited.

  4. 04

    Serve it like software

    Typed outputs, retries on schema failure, a timeout budget, and a dashboard that separates model errors from retrieval errors. A prompt with no version number is an incident waiting for a date.
