§01 — Case files

Three engagements, told the way they happened

Case File 01 — Loops · Class 01

The $47,900 weekend

CLIENT: B2B SaaS, ~400 staff
SUPPORT-TRIAGE AGENT, 6 TOOLS

The brief

A support-triage agent — the same shape as the run in §01 of the index — had been live for five months and was, by every dashboard, fine. Then the monthly model invoice arrived at roughly six times the forecast, and the team asked the only question that mattered: where did it go? There were no error spikes to investigate. Nothing had crashed. The traces existed but nobody had ever read twenty of them in a row.

The decisions

The trace review came first, before any fix was proposed. Reading the weekend's runs in sequence showed the pattern within an hour: on tickets where a billing lookup returned an ambiguous result, the agent re-asked with a wider window, then a wider one, then rephrased — a median run cost of $2.65 against a healthy $0.08, across 9,800 weekend tickets. The fix was specified as guards, not prompt edits: a hard cap of 12 steps per run; repeated-call detection that halts on a third materially-identical call; a per-run budget cap of $0.50 with the halt logged as a first-class event; and a daily spend alarm set at the forecast, not at six times it. The hardening sprint installed all four on the client's own stack.

The outcome

Median run cost returned to $0.08 and the p95 settled at $0.41 — the honest price of the genuinely hard tickets. In the six months following, the repeated-call guard halted 214 runs; every one was a loop that would previously have billed until it timed out. The client's Head of AI Platform's testimonial is attached to this file on the index page, where it belongs.

Case File 02 — Silent wrong answers · Class 04

The upgrade that passed the demo

CLIENT: CONSUMER FINTECH
SUPPORT COPILOT, 11 TOOLS

The brief

A support copilot was due a model upgrade: cheaper per token, faster, and — on the vendor's demo script and the team's own twenty scripted scenarios — flawless, 20 out of 20. The team had been burned before by a change that "passed everything and broke production", and commissioned an evaluation harness before the rollout rather than after it.

The decisions

The harness was built from the client's real work, not from scenarios written for the occasion: 240 held-out tickets, graded by the client's own support leads against a written rubric, frozen before the new model ever saw them. Held-out matters — a set the builders can see becomes a set the system is tuned to, and stops measuring anything. On that set the upgrade scored 79% task success against the incumbent's 87%. The traces found the cause: the new model emitted one tool's arguments in a subtly different shape, and the client's parser silently defaulted the missing field — every affected call "succeeded" and searched the wrong account segment. Two fixes followed: strict schema validation that rejects malformed calls instead of defaulting them, and the harness wired into the release pipeline as a gate a model change must pass to deploy.

The outcome

The upgrade was blocked, the vendor informed with traces attached, and a corrected version passed the same gate five weeks later. Three further upgrades have since gone through the gate; one was rejected. The set has grown to 310 cases — every production failure the team finds is graded and added, so the harness gets stricter as the system gets older, which is the correct direction.

Case File 03 — Tool misuse · Class 02

Write access, removed

CLIENT: LOGISTICS OPERATOR
INTERNAL OPS AGENT, 14 TOOLS

The brief

An internal operations agent saved the team real hours: it chased shipment exceptions, updated customer records and issued refunds for damaged consignments. It also held, in one undifferentiated toolset, the ability to do all of that directly and irreversibly — refund any amount, edit any record, with no approval step and no preview. Nothing had gone visibly wrong yet. The operations director's brief was one sentence: "Tell me what this thing can do on its worst day."

The decisions

The design review mapped every tool by reversibility, and the redesign followed that single line. Reads stayed free — an agent that must ask permission to look things up is a slow search box. Writes were split: every write tool gained a dry-run mode that renders exactly what would change, refunds above £50 and any record deletion moved to a human approval queue, and every executed write wrote an audit entry a person could replay. The agent kept all fourteen tools; what it lost was the ability to use eleven of them unobserved. This is the part of agent design nobody demos: the demo is the capability, the product is the permission structure around it.

The outcome

The irreversible-action failure class closed: in the first quarter under the new structure, 1,140 write actions were previewed, 96 went to the approval queue, and 7 were rejected by approvers — each rejection a small, cheap save. The median approval decision took four minutes, so the team's hours saved survived the change. The agent kept its job. It lost its pen.
