Case file 01 · Security review

The setter that wasn’t gated

Type
Pre-launch security review
Client
DAO tooling team (name withheld)
Scope
3 contracts · ≈1,900 lines
Duration
2 weeks
Status
Complete — launched after fixes

The brief

A treasury vesting system, two weeks from a launch the team had already announced publicly. The code was written, the tests were green, and the team wanted a review mainly as a formality — which is precisely when a review earns its fee.

The decisions

Read the specification against the code before reading the code alone. Then trace every state-changing function back to its authorisation check, by hand, in a table — no sampling. And when the launch date pressed, decline to compress the re-review of the fixes: the re-review is the review.

The outcome

Fourteen findings: 1 high, 3 medium, 10 low or informational, each answered in writing. The high finding was an access-control flaw at class level: a configuration setter verified the admin role, but the function it configured did not — the protection was on the door, not on the room. Fixed, re-reviewed, and launched nine days late by the client’s own decision. The testimonial on the overview page is from this engagement.

Case file 02 · Gas optimisation

A third off every claim

Type
Gas optimisation pass
Client
Token distribution platform (name withheld)
Scope
1 distributor contract
Duration
1 week
Status
Complete — live

The brief

A vesting distributor whose users claim in small amounts. At the client’s modelled volume, the per-claim transaction cost was eating the product’s margin — and being paid, in the end, by the users least able to pay it.

The decisions

Profile where the gas actually went before touching anything: storage layout first. Pack the claim record into fewer storage slots, remove one redundant external call, and change nothing about behaviour — every optimisation proven against the original test suite plus property tests on the claim maths.

The outcome

At the client’s modelled 40,000 claims a year, that is ≈34.7 ETH a year. Their volume, their model — my job was the per-claim figure, and that one is measured, not modelled. The estimator in §02 of the overview shows the same multiplication.

Case file 03 · Integration

Testnet first, caps on, then live

Type
Integration engagement
Client
Payments firm (name withheld)
Scope
Checkout integration with an existing euro stablecoin contract
Duration
6 weeks
Status
Complete — live

The brief

A payments firm adding a crypto checkout option against a stablecoin contract it did not write and could not change. Their condition, stated in the first meeting: a smart-contract incident must never be allowed to become a payments incident.

The decisions

Test against a fork of live chain state before any testnet deployment — the contract’s real behaviour, not its documentation. Stage the rollout with per-transaction and daily caps in the client’s own systems, where their controls live. And rehearse the kill switch before launch, in a drill, not for the first time during an incident.

The outcome

Live in six weeks. Caps raised in two planned steps as the integration earned trust. Zero incidents in the first ninety days. The artefact the client’s on-call team asked to keep was not the code — it was the runbook.
