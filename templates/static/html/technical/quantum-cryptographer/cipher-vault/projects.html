What a migration looks like from the inside

Six programmes, each with the constraint that made it hard: a five-year firmware cycle, a middlebox that rewrote handshakes, a board that wanted a quantum deadline it could put in a risk register.

CV-2604 · Embedded

ML-KEM on a fleet that cannot be reflashed twice

Utility meters · ARM Cortex-M4 · 240 MHz

The meter fleet had 96 kB of flash headroom and a bootloader that could only be updated once, by design: a failed flash in the field means a truck roll. The vendor wanted ML-KEM-768 for the next key rotation, and the obvious port of the reference implementation did not fit — 34 kB of code plus a 6 kB stack peak against a 4 kB budget.

We rebuilt the NTT with a smaller precomputed table, moved the matrix generation to the server side of the protocol where it belonged, and measured the result on the actual silicon rather than on a development board. Decapsulation settled at 1.42 million cycles and the stack high-water mark at 3.6 kB. The hybrid path kept X25519 as the fallback for the 4,100 meters that would receive firmware on the older radio.

CV-2602 · Inventory

1,840 endpoints in nine days, and the 214 keys nobody owned

Regional bank · TLS, mTLS, code signing

The bank believed it had 1,200 TLS endpoints. Certificate transparency, load-balancer configuration and a scan of the mobile apps produced 1,840, of which 214 had no owner in the configuration management database. Eleven were leaf certificates for internal services that had been decommissioned but not shut down.

The inventory was built as a CSV with a fixed schema and a second file describing how each row was discovered, so the next team can re-run it. We also recorded the key type and the signature algorithm per endpoint, because "RSA-2048" and "ECDSA P-256" fail the 2030 deprecation test at different times.

The 214 unowned keys became a separate finding: 84 were revoked within the month, 61 turned out to belong to a subsidiary’s staging environment, and the rest were assigned owners after a week of asking. The CIO’s summary was three lines long.

RESULT 84 certificates revoked, 130 assigned, and a repeatable script handed to the platform team. The report is CV-TR-2026-02.

CV-2511 · Telecom

A middlebox that quietly downgraded the hybrid

Mobile network · TLS termination · 38 PoPs

The carrier had rolled out X25519 plus ML-KEM-768 to its customer-facing API and reported 100% coverage. A capture at one peering point showed 7% of sessions negotiating to X25519 alone. The cause was a TLS-terminating appliance that dropped any ClientHello over 1,400 bytes, and the client retried without the new key share — correctly, per the spec, and silently.

We instrumented the negotiation path to log the selected group and the reason for the fallback, then built a canary that alerts on any session where the hybrid is not selected. The fix was a configuration change on 11 appliances and a client-side flag that refuses to downgrade for high-value endpoints.

The lesson is in the report: a hybrid rollout is not complete when the code ships, it is complete when you can prove which group was selected on every path you care about.

CV-2507 · QKD

128 km of fibre, and a certificate problem

Data centre interconnect · decoy-state BB84

The operator wanted a QKD link between two data centres and expected the hard part to be the optics. The optics behaved: 128 km of installed fibre, 1.9 kbps of sifted key at 11% QBER on a warm afternoon, which is enough for a key-refresh channel and not enough for bulk encryption. The hard part was authenticating the classical channel that carries the sifting conversation.

QKD gives you a shared secret with information-theoretic security only if the parties can authenticate each other; otherwise the man in the middle is just another endpoint. The existing PKI was RSA-2048, which defeats the purpose. We designed the link to authenticate with ML-DSA-65 signatures on a separate channel, and documented the trust assumption rather than hiding it.

The link is now in production for key refresh on a backup circuit, with a clear note in the architecture record that it does not protect the traffic itself.

CV-2503 · Agility

Swapping a signature scheme in a week

Payment network · code signing · 4 HSM vendors

The network signed release artefacts with RSA-3072 on three HSM models, with the algorithm hard-coded in a Java service and duplicated in a Go tool. Adding ML-DSA meant touching nine repositories, four vendors and a certification body. We replaced the call sites with a signing interface that takes an algorithm identifier and a key handle, and moved the choice into configuration with a versioned key manifest.

The first real test was a swap from ML-DSA-65 to ML-DSA-87 on one product line: it took four days, including the HSM firmware update and the re-issued key manifest. The same change would have taken a quarter before.

The interface is deliberately boring. Boring is what survives an acquisition.

RESULT Algorithm selection is configuration, not code. Two schemes run in parallel and a third can be added without a release. The report is CV-TR-2025-03.

CV-2606 · Firmware

Signing 30 MB images with a 2.4 kB signature

Industrial gateway · secure boot · 12-year support

The gateway verified firmware with RSA-2048 and a 12-year support commitment, which is exactly the horizon where a quantum break becomes someone’s problem. The constraint was the boot ROM: 8 kB of mask ROM, no possibility of a field update, and a verification path that had to run before any mutable code.

ML-DSA-44 verification fitted in 6.1 kB of ROM with a 2.4 kB signature expansion per image, and the key size stayed within the OTP fuse budget. SLH-DSA was rejected on signature size — 7.8 kB for the smallest parameter set, against a 30 MB image that was already tight on the recovery partition.

The migration runs both verifiers for two product generations, with the new key in a separate fuse bank. The boot ROM change is in the next mask revision; the fielded units get the dual verifier through the existing update path.
